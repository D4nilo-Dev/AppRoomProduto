Parte A:
A1 -> Após a inserção bem-sucedida de um produto no banco de dados, o conteúdo de todos os campos de texto é redefinido com o método `clear()`, e o foco do cursor volta automaticamente para o campo de nome utilizando `requestFocus()`.
A2 -> Implementada uma validação condicional antes da montagem do objeto de produto. Caso o utilizador tente gravar com o campo de preço vazio, com valor zero ou número negativo, o fluxo é interrompido com return@setOnClickListener e um aviso de erro é exibido diretamente no campo através de binding.editProductPrice.error.
A3 -> Foi adicionado um TextView no layout XML (activity_main.xml). Ao clicar no botão de listar produtos, a lista retornada pelo método getAll() do DAO é convertida numa cadeia de texto estruturada e apresentada diretamente no ecrã da aplicação.
A4 -> Junto à listagem de produtos, foram empregues funções da biblioteca padrão do Kotlin (products.size e products.sumOf { it.price }) para calcular e exibir no ecrã a quantidade de produtos cadastrados e a soma total dos seus preços.
A5 -> Adicionada uma consulta SQL com a cláusula LIKE na interface ProductDao. No layout, foram inseridos um campo de busca e um botão. Ao pesquisar, o texto introduzido é envolvido por % para permitir a localização de registos com correspondência parcial.
A6 -> Foi criado o método deleteAll() no DAO anotado com @Query("DELETE FROM product"). Na interface, foi configurado um botão "Excluir Todos" que chama essa função assíncrona e limpa a visualização de texto no ecrã.
A7 -> Adicionadas as funções findById e @Update no DAO. No layout, foram adicionados campos para informar o ID e o novo preço. O app localiza a entidade existente pelo ID, cria uma cópia com o preço atualizado usando .copy() e persiste a alteração no SQLite.
A8 -> Adicionou-se o atributo quantity: Int à entidade Product e o respetivo campo de introdução no layout. A versão da base de dados foi incrementada de 1 para 2 na anotação @Database(entities = [Product::class], version = 2).


Parte B:
B1 -> Persistência significa salvar os dados no armazenamento do celular para que nada se perca ao fechar o app ou desligar o aparelho. Se usássemos apenas uma MutableList, os produtos ficariam guardados só na memória RAM. O problema disso é que, ao fechar o aplicativo ou simplesmente girar a tela, a Activity seria reiniciada e a lista seria completamente apagada. O Room evita isso gravando tudo no banco SQLite.
B2 -> Mexer no SQLite "na mão" dá muito trabalho: temos que escrever comandos SQL como texto puro e converter tabelas para objetos linha por linha. O Room facilita isso sendo uma camada inteligente sobre o banco. Duas grandes vantagens dele são: ele avisa se houver erro no SQL logo ao compilar (evitando que o app trave na mão do usuário) e se integra perfeitamente com Kotlin e corrotinas para rodar tudo fora da thread principal sem complicação.
B3 -> Essas três peças dividem o trabalho do banco de forma organizada:   Entity: é a classe (Product.kt) que representa a tabela e suas colunas.   DAO: é a interface (ProductDao.kt) onde colocamos os comandos do banco, como inserir, listar e apagar.   Database: é a classe central (AppDatabase.kt) que cria o arquivo do banco e conecta as entidades aos DAOs.   No projeto, a tela pede o DAO ao Database para conseguir salvar ou buscar os produtos da Entity. 
B4 -> A thread principal cuida de desenhar a tela e responder aos toques do usuário. Se colocarmos operações demoradas nela, como ler o banco de dados, o aplicativo congela e o Android exibe o erro de ANR (Application Not Responding), sugerindo fechar o app. O suspend avisa que a função pode pausar sem travar a tela, e o lifecycleScope.launch roda essa tarefa em segundo plano, cancelando-a com segurança se a tela for fechada.
B5 -> O fallbackToDestructiveMigration() serve para o Room apagar o banco inteiro e criá-lo do zero caso a estrutura mude e o número de versão aumente. Em testes isso é prático, mas num app publicado na Play Store seria péssimo, pois apagaria todos os dados reais dos clientes. Uma migração (Migration) correta é escrever um código SQL que altera a tabela existente (adicionando uma coluna nova, por exemplo) sem perder nada do que já estava salvo.
B6 -> O ViewBinding cria referências automáticas e diretas para todos os elementos do XML. A grande vantagem frente ao antigo findViewById é a segurança: não corremos o risco de errar o tipo do componente (como confundir botão com texto) nem de tomar erro de NullPointerException por digitar o ID errado. Se o componente existe no layout, ele já aparece pronto para uso no código com o tipo certo.
B7 -> Criar a conexão com o banco de dados é um processo pesado para o processador e para a memória. No tutorial criamos na MainActivity por simplicidade, mas num app maior com várias telas isso causaria problemas. Se cada tela criasse seu próprio banco, teríamos múltiplas conexões disputando o mesmo arquivo no disco, gerando lentidão e conflitos. Usar Singleton garante que o app todo compartilhe uma única instância aberta.
B8 -> A maior dificuldade foi entender o fluxo das corrotinas e garantir que os dados atualizados fossem refletidos na tela sem erros de compilação. Um exemplo prático de uso do Room seria em um aplicativo de controle de pedidos para garçons em restaurantes. Com o Room, o atendente consegue registrar os pedidos e conferir o cardápio mesmo se o Wi-Fi do salão cair momentaneamente, sincronizando tudo com a cozinha assim que o sinal voltar.
